# คู่มือ staging และตรวจความเสี่ยง — www.ncmad.com

## 1. เตรียมข้อมูลโดยไม่ส่งรหัสผ่าน

- สิ่งที่ใช้วางแผนได้ทันที: เวอร์ชัน WordPress/PHP และชนิดกับเวอร์ชัน DB (MySQL หรือ MariaDB), รายชื่อธีม/ปลั๊กอินพร้อมเวอร์ชัน, โครงสร้างเว็บ (เว็บเดียวหรือ Multisite, ติดตั้งที่ root หรือใน subdirectory), และรายการฟังก์ชันสำคัญ เช่น ฟอร์ม รับเงิน อีเมล หรือระบบสมาชิก ตรวจจาก Site Health/หน้าจัดการโฮสต์แล้วตัดข้อมูลลับออกก่อนส่ง
- ให้เจ้าของเว็บหรือโฮสต์ทำ backup ไฟล์และฐานข้อมูล เก็บต้นฉบับเข้ารหัสและทดสอบความครบถ้วนในพื้นที่ควบคุม หากต้องรับส่งไฟล์ใช้ SFTP/SSH หรือช่องทางเข้ารหัสของโฮสต์แทน FTP ธรรมดา ไม่ส่งรหัสผ่าน, `wp-config.php`, database dump จริง หรือ API keys ผ่านแชตหรือ Git
- ทำ **สำเนาสำหรับ staging** แยกจาก backup ต้นฉบับ และลบ/แทนที่ข้อมูลส่วนบุคคล ข้อมูลคำสั่งซื้อ อีเมล รหัสผ่านและแฮชเดิม tokens, SMTP/OAuth/payment keys, webhooks และการตั้งเวลา/คิวงานที่ค้างอยู่ ตรวจตารางของปลั๊กอินและไฟล์ด้วย ไม่ใช่เฉพาะตาราง `users` ถ้าทำสำเนาที่ปลอดภัยไม่ได้ ให้ใช้ข้อมูลทดสอบสังเคราะห์ก่อน
- ถ้าโฮสต์ต้องให้สิทธิ์ผู้ปฏิบัติงาน ให้ใช้บัญชีชั่วคราวขอบเขตต่ำสุดผ่านระบบจัดการความลับขององค์กร และปิดสิทธิ์ภายหลัง สำหรับการตรวจเว็บจริงให้ตกลงขอบเขต ผู้อนุมัติ ช่วงเวลา และเงื่อนไขหยุดงานก่อน

## 2. กู้คืนที่ local โดยยังไม่เปิดหน้าเว็บ

คำสั่งด้านล่างเป็นตัวอย่างสำหรับ **single-site ติดตั้งที่ root** บน Bash (Linux/macOS/WSL) ถ้าเว็บจริงใช้ Multisite, subdirectory, โครงสร้างแยก core/config, หรือ DB ใช้ collation ที่ MariaDB ไม่รองรับ ให้ปรับขั้นตอนกู้คืนก่อนนำเข้า ไม่ใช้คำสั่งชุดนี้ตรง ๆ

1. เตรียม Docker/Python ตาม [README](../README.md) แล้วรัน `python3 staging/init_env.py` ครั้งเดียว ตรวจ `.env` ให้ `STAGING_TABLE_PREFIX` ตรงกับ dump เช่น `wp_` ค่าของ `STAGING_WP_IMAGE` และ `STAGING_CLI_IMAGE` ใช้ PHP สายเดียวกัน เริ่มจากเวอร์ชัน core/PHP ที่ตรงหรือเข้ากันได้เพื่อวัด baseline ก่อนอัปเกรด ตรวจ engine/collation ของ dump ด้วย ตัวอย่าง Compose นี้ใช้ MariaDB และไม่รองรับการสลับเป็น MySQL เพียงเปลี่ยน tag (การตั้งค่าและ healthcheck ต่างกัน)
2. เก็บไฟล์นอก repo หรือใน `staging-data/` ที่ถูก ignore ตัวอย่างด้านล่างสมมติว่า `staging-data/sanitized.sql` เป็น SQL ของฐานข้อมูล WordPress เดียว ไม่สั่ง `CREATE DATABASE` หรือ `USE` ไปยังชื่อเดิม ต้องเป็นฐาน staging ว่าง ไม่ทับเว็บจำลองที่มีข้อมูลเดิม และอย่าใส่รหัสผ่านเว็บจริงใน `.env`

```sh
# หยุด gateway ก่อนหากเคยเปิดไว้ ใช้ฐานข้อมูล staging ว่างเท่านั้น
# docker compose --profile browser stop gateway
docker compose up -d --wait db wordpress

docker compose exec -T db sh -c \
  'MYSQL_PWD="$MARIADB_PASSWORD" exec mariadb --user="$MARIADB_USER" "$MARIADB_DATABASE"' \
  < staging-data/sanitized.sql
```

3. ใช้ WP-CLI เปลี่ยน URL แบบรองรับข้อมูล serialized ใช้ **URL จริงจาก inventory** รวมทุกแบบที่พบ (`http`/`https`, `www`/ไม่มี `www`) คำสั่งนี้เป็นตัวอย่างแบบ `https://www.ncmad.com` ให้ดูผล `--dry-run` ก่อนแล้วจึงรันจริง ทำ **ก่อน** คัดลอกโค้ดปลั๊กอินหรือธีม เพื่อไม่ให้ CLI ต้องโหลดโค้ดจากสำเนาที่ยังไม่ได้ตรวจ

```sh
docker compose run --rm cli wp --skip-plugins --skip-themes search-replace \
  'https://www.ncmad.com' 'http://127.0.0.1:8088' \
  --all-tables-with-prefix --skip-columns=guid --dry-run

docker compose run --rm cli wp --skip-plugins --skip-themes search-replace \
  'https://www.ncmad.com' 'http://127.0.0.1:8088' \
  --all-tables-with-prefix --skip-columns=guid
```

4. เพิ่มบัญชีผู้ดูแล staging ด้วยอีเมลและรหัสผ่านทดสอบ (WP-CLI จะแสดง prompt ให้กรอก ไม่ใส่รหัสในคำสั่ง) หากขึ้นข้อความให้ปรับ schema ให้บันทึก checkpoint ก่อนดำเนินการ

```sh
docker compose run --rm cli wp --skip-plugins --skip-themes user create \
  local-reviewer local-reviewer@example.invalid --role=administrator --prompt=user_pass
```

5. คัดเฉพาะ `uploads` ที่ตรวจแล้วว่าเป็นสื่อที่อนุญาตและไม่มีไฟล์รหัสหรือข้อมูลลับ ตัวอย่างนี้คัด **เนื้อหาใน** `staging-data/uploads/` ไปยังโฟลเดอร์ uploads จากนั้นติดตั้งธีม/ปลั๊กอินที่ต้องใช้จากแพ็กเกจที่ตรวจแหล่งที่มาและตรวจเวอร์ชันแล้ว อย่าคัด `wp-config.php`, `.htaccess`, cache, backup, drop-ins (`object-cache.php`, `db.php`, `advanced-cache.php`) หรือ MU plugins เดิมมาทั้งชุด ถ้าเว็บจริงจำเป็นต้องใช้รายการเหล่านี้ ให้ตรวจโค้ด/ค่าเชื่อมต่อก่อนจำลองแยกต่างหาก ชุดนี้กำหนดพื้นที่ MU เฉพาะเพื่อปิดอีเมล

```sh
docker compose exec -T wordpress mkdir -p /var/www/html/wp-content/uploads
docker compose cp staging-data/uploads/. wordpress:/var/www/html/wp-content/uploads/
docker compose exec -T wordpress chown -R www-data:www-data /var/www/html/wp-content/uploads

docker compose up -d --wait gateway
curl -fsS -o /dev/null -D - http://127.0.0.1:8088/
```

6. เปิดจากเบราว์เซอร์โปรไฟล์แยก ไม่ใช้ session เว็บจริง ตรวจว่าไม่มี redirect ไปโดเมนจริงหรือ third-party traffic ผ่าน DevTools ถ้าพบให้หยุด gateway และแก้ config ก่อนนำมาทดสอบต่อ ตรวจหน้าหลัก, `/wp-admin/`, permalinks, รูปภาพ และ error logs (`docker compose logs --tail=100 wordpress db gateway`) ฟอร์มและ checkout ควรใช้ข้อมูลตัวอย่างและจำลองบริการที่ต้องเชื่อมต่อ ไม่ปลดการป้องกันเพื่อยิงระบบชำระเงิน/อีเมลจริง CSP ของ staging อาจบล็อก CDN/แผนที่/สคริปต์บางส่วน อย่านำ policy นี้ไปใช้จริงโดยไม่ซ้อมผลกระทบ

## 3. ตรวจความเสี่ยงและจัดลำดับแก้ไข

รายการต่อไปนี้คือ **แผนตรวจ ไม่ใช่ช่องโหว่ที่ยืนยันแล้วของเว็บจริง** ใช้ inventory จากโฮสต์/แอดมินและ logs แบบอ่านอย่างเดียวเทียบกับประกาศจากผู้ผลิต ปลั๊กอิน และ CVE ที่เกี่ยวข้อง ตรวจเวอร์ชันที่ได้รับผลกระทบและเวอร์ชันที่แก้แล้วก่อนตัดสินใจ

| ลำดับ | สิ่งที่ตรวจ | แนวทางแก้ไข/ป้องกัน |
| --- | --- | --- |
| เร่งด่วน | มีหลักฐานบัญชีถูกยึด, เว็บส่งสแปม, redirect ผิดปกติ, ไฟล์หรือแอดมินที่ไม่รู้ที่มา หรือซอฟต์แวร์ที่โดนโจมตีจริงหรือไม่ | เก็บ logs/หลักฐานก่อนเปลี่ยนแปลง ประสานโฮสต์เพื่อจำกัดผลกระทบ เปลี่ยน secrets จากเครื่องที่เชื่อถือได้ และกู้คืนจากสำเนาที่ตรวจแล้ว ไม่พึ่งการอัปเดตอย่างเดียวเมื่อสงสัยว่าเว็บถูกเจาะ |
| สูง | Core/PHP/DB/ธีม/ปลั๊กอินหมดระยะสนับสนุนหรือมีประกาศช่องโหว่ตรงเวอร์ชันหรือไม่ | อัปเดตเป็นรุ่นที่แก้แล้วและยังรองรับหลังซ้อมบน staging ถ้าไม่มีรุ่นแก้ให้ถอดหรือเปลี่ยนส่วนเสริมที่ไม่ได้รับการดูแล |
| สูง | สิทธิ์ผู้ดูแลและ DB เกินจำเป็นหรือไม่, เปิด FTP/DB สู่สาธารณะหรือไม่, ใช้ HTTP ในการล็อกอินหรือไม่ | เปิด MFA, ลดสิทธิ์, ปิดบัญชีเก่า, ใช้ SFTP/SSH แทน FTP, จำกัด DB ไว้ในเครือข่ายที่จำเป็น, ตั้ง HTTPS และตรวจโดเมนหลัก/redirect/certificate |
| กลาง | มี backup ที่กู้ได้จริงหรือไม่, upload directory รัน PHP ได้หรือไม่, logs/alerts และการอัปเดตมีผู้รับผิดชอบหรือไม่ | ซ้อม restore, เก็บ backup นอกเว็บรูท, ปิดการรัน PHP ใน uploads ที่เว็บเซิร์ฟเวอร์จริง, ตั้ง alerts และจำกัดการลองล็อกอินโดยตรวจผลกระทบต่อผู้ใช้ |

รายงานแต่ละรายการด้วยหลักฐานที่ไม่รวมข้อมูลลับ, ผลกระทบ, ระดับความเสี่ยง, วิธีแก้, ผู้รับผิดชอบ และผลตรวจซ้ำ ไม่ทดสอบเจาะระบบจริงหรือทดลอง exploit เป็นส่วนหนึ่งของแผนนี้

## 4. ซ้อมอัปเกรดและวางแผน rollback

1. **เก็บ baseline และ checkpoint:** จดเวอร์ชันอิมเมจจริง (tag/digest), รายการปลั๊กอินและค่า config ถ่ายสำเนาฐานข้อมูลและไฟล์ staging ณ จุดเดียวกันโดยหยุดการเขียนก่อน เก็บนอก Git ทดสอบว่ากู้ DB และไฟล์กลับมาใช้งานได้จริง
2. **อัปเกรดทีละชุดตาม compatibility:** อ่านข้อกำหนดของปลั๊กอิน/ธีมและโฮสต์ก่อนเลือกเส้นทาง ซ้อมการเปลี่ยน core, ส่วนเสริม, PHP และ DB เป็นขั้นตอน วัดผลหลังแต่ละจุด ใช้แพ็กเกจจากแหล่งที่เชื่อถือได้และนำเข้าแบบออฟไลน์ อย่าคาดว่าเปลี่ยน tag ของ WordPress แล้ว core ใน volume จะอัปเดตเอง: อิมเมจเริ่มต้นคัด core เมื่อ volume ยังไม่มี WordPress ต้องซ้อมการอัปเกรด core/DB แยกต่างหาก สำหรับการเปลี่ยนสาย DB ให้ใช้ volume ใหม่และทดสอบการย้ายข้อมูล ไม่สลับ image ทับ volume เดิม
3. **เกณฑ์ผ่าน:** หน้าและ URL สำคัญเปิดได้, login/สิทธิ์ทำงาน, ภาพ/ลิงก์ไม่ชี้เว็บจริง, ฟอร์ม/ขั้นตอนสั่งซื้อผ่านในโหมดจำลอง, ไม่มี fatal error ใหม่, และกู้คืน checkpoint ได้ในเวลาที่ธุรกิจยอมรับ บันทึกผลให้เจ้าของเว็บอนุมัติก่อนแตะ production
4. **ขึ้นจริงเฉพาะในช่วงที่ตกลง:** ใช้ snapshot/backup ล่าสุดและทดสอบ restore กับโฮสต์ก่อน หากเว็บมีการเขียนข้อมูล (เช่น คำสั่งซื้อ) วางแผนช่วงหยุดรับข้อมูลสั้น ๆ หรือวิธีเก็บรายการหลัง snapshot ที่ตรวจสอบได้ ห้ามนำ DB staging ทับ production ใช้ระบบ staging/สลับ deployment ของโฮสต์เมื่อรองรับ แต่ไม่รับประกัน downtime เป็นศูนย์
5. **เงื่อนไขย้อนกลับ:** หน้า/หลังบ้านใช้งานไม่ได้, checkout หรือฟอร์มสำคัญเสีย, หรือ error เพิ่มผิดปกติ ให้หยุด rollout แล้วกู้ไฟล์ ฐานข้อมูล และ runtime จากชุดที่เข้าคู่กัน การย้อนเฉพาะไฟล์อาจไม่พอหลัง schema migration หลัง rollback ตรวจข้อมูลที่เกิดใหม่กับเจ้าของเว็บก่อนเปิดรับรายการอีกครั้ง
